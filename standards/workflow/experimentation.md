# Experimentation Standard

> **Experiments are how we turn hunches into knowledge.**

---

## Core Principles

1. **Falsifiability First:** A hypothesis that cannot be disproven is not a hypothesis. State concrete, measurable criteria before running the experiment.
2. **Honesty Over Advocacy:** Document what *happened*, not what you *wanted* to happen. Record failures, surprises, and confounds with the same care as successes.
3. **Controls Are Mandatory:** Every experiment must have a baseline. Without a control, you cannot attribute causation to your variable.
4. **Acknowledge Limitations:** Every experiment has weaknesses. Documenting them honestly strengthens the work — hiding them undermines it.

---

## Experiment Design

### 1. Define the Hypothesis

**Good:** *"B-Tree retrieval will reduce total token consumption by ≥30% compared to keyword search, while producing architecturally equivalent solutions."*

**Bad:** *"B-Tree retrieval will improve agent performance."*

### 2. Identify Variables

| Variable Type | Definition | Example |
| :--- | :--- | :--- |
| **Independent** | What you deliberately change between arms | Retrieval method (B-Tree vs. keyword search vs. none) |
| **Dependent** | What you measure as outcomes | Token consumption, context window usage, human interventions |
| **Controlled** | What you hold constant across all arms | Model, seed, temperature, prompt, baseline commit, hardware |

Document all three types explicitly in the Method section.

### 3. Design Controls

The control arm must use the same prompt, model, seed, and environment as the variable arms.

**Control types:**

| Type | When to Use |
| :--- | :--- |
| **Negative control** (no treatment) | Default — test the variable's presence vs. absence |
| **Positive control** (known-good treatment) | When validating that your measurement apparatus works |
| **Active control** (alternative treatment) | When comparing two approaches rather than presence vs. absence |

### 4. Address Confounds Up Front

Before running, list known threats to validity:

- **Selection bias:** Are the arms truly comparable, or does one start with an advantage?
- **Prompt sensitivity:** Would small wording changes reverse the result?
- **Hardware/environment variance:** Are runs on the same machine, same load, same model version?
- **Observer bias:** Does the experimenter know which arm is which? Does that influence their behavior?

Document confounds and assess their impact — not all can be eliminated.

### 5. Determine Sample Size

| Context | Guidance |
| :--- | :--- |
| Exploratory pilot / engineering case study | N=1 per arm is acceptable if honestly labeled as exploratory. Use multi-tier prompt matrices to add breadth. |
| Directional claims for a whitepaper | N≥3 per arm (different seeds), or multi-tier design showing consistent direction across conditions |
| Strong causal claims | N≥10 per arm with statistical testing (confidence intervals, effect sizes). Rarely needed for our work. |

State your sample size and justify it. *"N=1 per arm; this is an exploratory pilot. Findings are directional, not confirmatory."*

## Execution

### Checkpoints

Define data collection points **before** running the experiment. Each checkpoint must specify:

1. **When** it occurs (e.g., "end of planning phase," "after first Act completion")
2. **What** is recorded (exact metrics list)
3. **How** it is recorded (screenshot, API call, manual observation)

### Standard Metrics for Agent Experiments

When benchmarking AI agent performance, capture these metrics at every checkpoint:

| Metric | Definition | Unit |
| :--- | :--- | :--- |
| **Context Window** | Tokens currently in the model's context | tokens (and % of max) |
| **Prompt Tokens** | Cumulative input tokens sent to the model | tokens |
| **Completion Tokens** | Cumulative output tokens generated by the model | tokens |
| **Total Token Burn** | Prompt + Completion tokens | tokens |
| **Human Interventions** | Count and verbatim content of steering prompts | count + text |
| **Functional Correctness** | Does the solution work? (tests passing, runtime verified) | pass/fail + detail |
| **Architectural Fidelity** | Does the solution match design constraints? | qualitative assessment |
| **Git Workflow Adherence** | Branch naming, commit hygiene, working tree state | qualitative assessment |

### Intervention Protocol

Human interventions during an experiment are **data, not contamination** — but they must be handled consistently:

1. **Record the exact verbatim prompt** of any human intervention.
2. **Record the reason** for the intervention (agent asked a question, agent made a dangerous mistake, agent was stuck).
3. **Count interventions per arm** as a dependent variable.
4. **Do not steer variable arms differently from control** unless the steering itself is the finding (e.g., "memory eliminates the need for steering" is a valid conclusion when Control required steering and Variable did not).

## Multi-Phase Experiments

| Phase | Purpose | Example |
| :--- | :--- | :--- |
| **Phase 1: Initial Execution** | Measure first-pass performance across all arms | Plan + Act on the vague symptom prompt |
| **Phase 2: Follow-Up Repair** | Measure multi-turn correction overhead | Standardized symptom-fix prompt to reach functional parity |
| **Phase 3: Tier Variation** | Test robustness across prompt complexity levels | Same task with Tier 1 (vague), Tier 2 (technical), Tier 3 (directive) prompts |

Each phase should have its own checkpoints and metrics. **Complete all arms within a phase before starting the next phase** to avoid temporal confounds.

## Analysis & Reporting

### Methodological Notes Section

Every experiment document must include a **Methodological Notes** section between Results and Conclusions, covering:

1. **Acknowledged limitations** — sample size, confounds, scope constraints
2. **Mid-experiment discoveries** — things that turned out to be findings rather than flaws
3. **Scope of claims** — what the data supports vs. what it does not

### Comparative Analysis

When comparing arms:

- **Use ratios and percentages**, not just raw numbers ("3.65x context reduction" is more informative than "131k fewer tokens")
- **Compare at equivalent checkpoints** — don't compare one arm's Checkpoint 1 with another's Checkpoint 2
- **Distinguish quality parity from efficiency differences** — if two arms produce the same architectural plan, the comparison is about retrieval *efficiency*, not retrieval *quality*
- **Account for architectural divergence** — if arms produce different implementations (e.g., 2-table schema vs. indexed column), token differences may reflect implementation complexity, not retrieval method effectiveness

### Claim Strength

Match your language to your evidence:

| Evidence Level | Appropriate Language |
| :--- | :--- |
| N=1, single tier | *"In this exploratory run, we observed..."*, *"Directional evidence suggests..."* |
| N=1, multi-tier consistency | *"Across all prompt tiers, the pattern held..."*, *"Consistently observed..."* |
| N≥3, consistent direction | *"Results indicate..."*, *"The data supports..."* |
| N≥10, statistical testing | *"We found a statistically significant..."* |

## Checklist

Before starting any experiment, verify:

- [ ] Hypothesis is falsifiable with concrete metrics
- [ ] Independent, dependent, and controlled variables are documented
- [ ] At least one control arm is defined
- [ ] Known confounds are listed with impact assessment
- [ ] Sample size is stated and justified
- [ ] Checkpoints are defined with specific metrics
- [ ] Intervention protocol is agreed (when to steer, how to record)

Before concluding any experiment, verify:

- [ ] All arms have reached equivalent completion points
- [ ] Methodological Notes section documents limitations honestly
- [ ] Claims match evidence strength (see Claim Strength table)
- [ ] Raw data is preserved (token counts, verbatim prompts, screenshots)
